# The caller supplies the seed and the signing randomness, a deliberate departure from FIPS 204 Section 6

FIPS 204 Section 6 says: "Other than for testing purposes, the interfaces for key generation and signature generation specified in this section should not be made available to applications, as any random values required for key generation and signature generation shall be generated by the cryptographic module." This package departs from that "should" on purpose. Its `keygen` derives the key pair from a seed that the caller supplies, as `ML-DSA.KeyGen_internal` does, and its `sign` takes the signing randomness from the caller instead of from a random bit generator. The package draws no randomness, and the wasm module imports nothing. Three reasons decide it. The same API works across every binding, including runtimes and bindings that lack `crypto.getRandomValues`. Tests stay deterministic without mocks, because ACVP, Wycheproof, and the differential tests feed exact seeds and randomness through the functions that consumers call. And the caller keeps control of the random source. The arguments against a wasm randomness import, which are a JavaScript exception unwinding wasm frames, re-entrancy during an operation, and a hidden input, rule out only an import. They don't rule out the TypeScript layer drawing randomness itself, so this record doesn't rest on them.

## Consequences

- The README says that the package is not a FIPS 140 module, and that the caller must supply both the seed and the signing randomness from a cryptographically secure random source. FIPS 204 Section 3.6.1 asks for an approved random bit generator with at least 256 bits of security strength for an ML-DSA-87 seed. Whether `crypto.getRandomValues` meets SP 800-90 in each runtime is unverified.
- `sign` takes `randomness` as a required argument with no default. The deterministic variant needs the explicit value `"deterministic"`.
- `keygen` and `sign` reject an all-zero seed and all-zero signing randomness with a `RangeError`, to catch a buffer that was never filled. These are the only valid FIPS 204 inputs that the public API refuses. The deterministic variant's 32 zero bytes stay reachable through `"deterministic"`, and signatures made elsewhere with a key from the all-zero seed still verify.
- The config sets `MLD_CONFIG_NO_RANDOMIZED_API`, item 2 of record 0002, so the module has no randomized entry point to call by mistake.
- The composite private key holds only the 32-byte seed, and `keygen` and `sign` take exactly that seed.

## Considered options

- **Draw the randomness in the TypeScript layer with `crypto.getRandomValues`**, as noble does by default. It would follow FIPS 204's "should" more closely for the hedged variant, but it gives up all three reasons above.
- **Import randomness into the wasm module**, through a `randombytes` that the module calls. The requirement that the wasm module imports nothing rules it out, and it brings the three hazards of an import: an exception unwinding wasm frames, re-entrancy during an operation, and a hidden input.
