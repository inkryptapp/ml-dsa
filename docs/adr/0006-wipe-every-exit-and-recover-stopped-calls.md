# Wipe memory before every exit in one core function, drop a poisoned instance, let the next call recover a stopped call's instance, and never detach the buffer

The package copies seeds, secret keys, and signing randomness into an instance's linear memory, and upstream's own stack frames hold secret intermediates there too. So every call runs through one core function, `runCore` in `packages/ml-dsa/src/core.ts`, which wipes memory before the call returns or throws. On a healthy instance, the wipe is two fills after the SHAKE256 release: the wasm stack, and every byte from `__heap_base` to the end of memory. Between calls, memory then equals a fresh instance's memory byte for byte. Any exception while a call holds the instance poisons it, an exception from the package's own JavaScript or from a cleanup step included. The call zeroes the whole memory, static data included, and drops the instance, and the next call creates a new one. A non-zero upstream return code doesn't poison. It wipes and keeps the instance. The cleanup sits inline in the core's `finally` block, so the wipe still runs when too little engine stack is left to start a function call.

If the runtime stops a call midway, as on a `vm` timeout or a debugger's terminate command, no cleanup runs. A module-level `checkedOut` names the instance that a call holds, and the call clears it in the last statement of its `finally` block. A call that finds `checkedOut` set after its input checks marks that instance as zeroed, zeroes its whole memory, clears `checkedOut`, and runs on a new instance. An inner call, which a debugger or an export hook starts while another call holds the instance, takes the same path. The inner call succeeds. The outer call finds its instance zeroed and fails, and no call runs on the zeroed instance again. After creation, the package keeps only views of the memory's buffer, the layout numbers, and the export functions, never the `Memory` object, the exports object, or the instance, so no package code can detach the buffer.

This record revises one sentence of record 0003: "any exception out of an export poisons the instance: the wrapper zeroes it, drops it, and instantiates the cached `WebAssembly.Module` again". Any exception while a call holds the instance now poisons it, not only one out of an export, and so does an inner call that zeroed the instance. The next call creates the new instance, not the call that poisoned the old one. This record also revises one sentence of record 0005's **Inputs** consequence: "so no other code runs while the instance is mid-operation". The sentence still holds for the package's own code, but a debugger or an export hook can start an inner call there. This record also revises one sentence of record 0007: "Inside the core, the call poisons, wipes, and drops the instance, then throws the package `Error` with the engine error as `cause`". Right after a healthy cleanup, the core makes two calls that the **A zeroed instance never runs again** consequence describes: the lookup with `zeroed.has`, and the fill that follows when an inner call zeroed the call's instance. If either call overflows, `keygen` and `sign` throw the engine's error unchanged, and `verify` returns `false`. Memory is wiped by then. The **Memory** consequence of record 0005 still holds as written. This record adds the exports object and the instance to the `Memory` object that the package never keeps.

## Consequences

- **The `catch` blocks only assign.** The cleanup makes exactly four calls in three `try` blocks: the release, the two healthy fills, and the whole-memory fill, whose fallback is a loop over a 32-bit view that makes no call. A log line or a helper call added there can fail to start at the engine's stack limit and skip the wipe. `packages/ml-dsa/check/core-structure.ts` fails on any other call, `new`, or member read in the core's `catch` and `finally` blocks, and on any assignment beyond the ones that it lists.
- **The package `Error` comes late.** The core builds it only after the `finally` block, because `new Error(...)` can fail to start at the stack limit. Record 0007 holds what the caller then sees.
- **`checkedOut` is cleared at the end of the `finally` block.** The checkout sets `checkedOut` and empties the slot in adjacent plain assignments, before any input is written. The `finally` block starts with `if (checkedOut !== held) { poisoned = true; }`. Its last two statements put the instance back and clear `checkedOut`, so a call that the runtime stops anywhere earlier leaves `checkedOut` set for the next call. The clear runs only while `checkedOut` still names the call's own instance, so an inner call that the runtime stopped leaves its own instance named. Moving the clear up, or making it unconditional, leaves an instance and its secrets unwiped. The structural check pins these statements.
- **A zeroed instance never runs again.** A debugger can pause the outer call anywhere in its cleanup, after the first check. An inner call that runs from the debugger then zeroes the outer call's instance, and the outer call goes on to put that instance back in the slot. So the recovery adds each instance that it zeroes to a module-level `WeakSet`, and no call runs on an instance in that set, because the instance's static data is zero too. Right after a healthy cleanup, outside the `finally` block, where calls are allowed, the outer call looks its instance up in the set. If an inner call zeroed it, the outer call poisons, drops the instance from the slot, and zeroes it again. A poisoned outer call skips the lookup, because it zeroed its whole memory and put nothing back. The recovery marks the instance before it zeroes it, so a fill that fails to start at the engine's stack limit still leaves the mark. In Node, exit-matrix rows pause the outer call through `node:inspector` at every breakable point of the cleanup that it reaches, and run an inner call there.
- **An inner call fails the outer call.** After an inner call zeroed the outer call's instance, `keygen` and `sign` throw the package `Error`, and `verify` returns `false`. The `cause` is `undefined`, unless the outer call caught an exception or got a non-zero return code of its own.
- **A stopped call's secrets wait for the next call.** If the realm keeps running, they stay in memory until the next call zeroes them. If the realm ends, as on worker termination, the engine frees that memory unwiped. Two cases stay open, and both need a debugger, because outside tests only a debugger can start a call while another call is midway. A debugger can read wasm memory anyway.
  - After an inner call zeroed the outer call's instance, the outer call can go on and write secrets to it again. If the runtime then stops the outer call, no later call zeroes that memory.
  - A debugger can pause a call on its assignment `checkedOut = null`, in its clear or in its recovery. If a call started from that pause is then stopped, the paused call's assignment overwrites the name of the stopped call's instance, and no later call zeroes that memory.
- **The `grow` ban.** `grow`, `toResizableBuffer`, and `toFixedLengthBuffer` detach the buffer even at the maximum size. The package's views would then hold zero bytes, so the wipe would zero nothing. A lint bans the three member names, and the module check fails on any `memory.grow`.
- **`minify: false`.** Each pack config must set it, so the core keeps its name, appears exactly once in each shipped entry file, and stays checkable there.
- **V8 coverage, not Istanbul.** The coverage gate runs Vitest's V8 provider, because Istanbul inserts calls into the cleanup blocks, which must hold no call. The exit matrix alone must reach every statement, branch, and function of `packages/ml-dsa/src/core.ts`, and each `v8 ignore` hint needs a reason in `packages/ml-dsa/test/coverage-hints.ts`.
- **Recording only in tests.** The core writes its test record only while a module-level switch is on, and only the test-only entry point turns it on. The test record never holds the instance, its exports, its memory, a view, or a byte array, so it can't keep secrets reachable.
- **Upstream zeroization stays unchanged.** The build keeps `mld_zeroize`, `MLD_FREE`, and `mld_shake256_release` as upstream ships them, and leaves `MLD_CONFIG_CUSTOM_ZEROIZE` unset. The package's own wipe is its only zeroing guarantee. In Node, the upstream residue test fails if the wasm stack after any export call of keygen or sign differs across 20 seeded rounds.

## Considered options

- **A cleanup function.** Reaching it needs a call, which can fail to start at the engine's stack limit.
- **A release on a poisoned instance.** It runs module code on an instance that has already failed, and the whole-memory fill zeroes the SHAKE256 state anyway.
- **Poisoning on a non-zero return code.** The instance stays healthy, and the two fills already restore a fresh instance's memory, so a drop would only cost an instantiation.
- **Leaving a stopped call's instance to the garbage collector.** Its memory keeps the secrets until the engine collects it, and code in the realm can still reach a dropped instance. In V8, `getThis()` on a trap's call sites returns it.
- **Keeping the `Memory` object, the exports object, or the instance.** Package code could then reach `grow` and detach the buffer.
- **Minified shipped files.** A minifier renames the core and can merge its blocks, so the structural check couldn't find the core or check its blocks.
- **Istanbul coverage.** Its counters are calls inside the cleanup blocks, so the gate would measure a cleanup that can fail to start at the stack limit.
- **More checks of `checkedOut` inside the `finally` block.** A debugger can still pause on the statement after the last check, and the cleanup can't call `zeroed.has`, which would catch it.
- **Tracking the instance of an outer call until its own cleanup runs.** The core can't tell a stopped call from one that a debugger paused. So every later call would zero the instance of every stopped call again, a fill of the whole memory each time, and the engine could never collect that instance.
- **A custom upstream zeroize.** `MLD_CONFIG_CUSTOM_ZEROIZE` would add a config difference, and the package's guarantee would still rest on its own fills.
