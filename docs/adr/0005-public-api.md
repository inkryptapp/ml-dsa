# Expose plain-byte functions with named arguments that sign from a seed, and stream every message through upstream's SHAKE256

The public API is three frozen objects, `mlDsa44`, `mlDsa65`, and `mlDsa87`, each with `keygen(seed)`, `sign({ seed, message, randomness, context })`, and `verify({ publicKey, message, signature, context })`. Named arguments keep the seed and the signing randomness from being swapped without the ceremony of branded types, so brands stay internal, for wasm pointers. Signing always starts from the seed, as the composite stores it, so no expanded secret key enters or leaves JavaScript, at a cost of 27 to 37% per signature. No message length cap exists. The wrapper feeds the message to upstream's SHAKE256 in 64 KiB chunks and passes the result as an external mu to `signature_internal` and `verify_extmu`, so `verify` never throws and never rejects a valid signature because of its length. Upstream's own signing and verification functions would frame the message themselves. Here, the domain-separation prefix still comes from upstream's `prepare_domain_separation_prefix`, but the absorb order (public-key hash, prefix, message chunks, then a 64-byte squeeze) lives in the wrapper, in one function that `sign` and `verify` share, and ACVP's pure-interface vectors cover it. The mu path handles no secret, because the public-key hash, the prefix, and the message are all public. The API is synchronous, and the module compiles when the package loads, so a blocked compile fails the import instead of turning every `verify` into `false`.

## Consequences

- **Exports.** The module exports 20 symbols: `memory`, `__stack_low`, `__stack_high`, `__heap_base`, and `__heap_end`; `keypair_internal`, `signature_internal`, and `verify_extmu` for each parameter set; `mldsa44_prepare_domain_separation_prefix` alone, because the prefix doesn't depend on the parameter set; and `mldsa_shake256_init`, `_absorb`, `_finalize`, `_squeeze`, and `_release`. Upstream's `verify` isn't exported. The committed export list records each export's name, kind, and wasm type. A snapshot of the C declarations behind them and a generated `_Static_assert` probe of the sizes the wrapper allocates guard the C side. The five SHAKE256 functions, the external-mu entry points, and the prefix function are pin-bump review items.
- **Memory.** `--initial-memory=327680`, fixed, with a 196,608-byte stack and a 64 KiB chunk. One committed JSON file holds the memory, stack, and chunk sizes. The flake reads it with `builtins.fromJSON` and passes the two build sizes as environment variables, and the wrapper inlines the rest at pack time. With clang 22.1.5 at the pin, ML-DSA-87 signing peaks at 112,353 bytes of stack, which leaves 84,255 bytes (43%) of headroom. The stack-margin test fills the stack with three patterns, runs every operation, and fails the check when a peak passes 75% of the stack. After creation, the package keeps only its views of the memory's buffer, the layout numbers, and the exported functions. It never keeps the `Memory` object, so no package code can call `grow`, `toResizableBuffer`, or `toFixedLengthBuffer`, which detach the buffer even at the maximum size. Two backstops guard that rule. On the source side, a lint ban rejects the three member names. On the module side, a check decodes the module's instructions and fails on any `memory.grow`, which would detach the buffer from inside the module.
- **One sign call.** Keygen runs in wasm, the public-key hash is read from the derived secret key, the message streams through SHAKE256, the signature uses the external mu, and everything is wiped. `verify` computes the public-key hash from the public key through the same exports. The SHAKE256 state is released only on a healthy instance, and a cleanup error never replaces the first failure.
- **Inputs.** A byte input is a `Uint8Array` from any realm over a fixed-length, non-shared, non-detached `ArrayBuffer`. The checks read it only through six getters that the package looks up once at load: `Symbol.toStringTag`, `buffer`, `byteOffset`, and `length` from `%TypedArray%.prototype`, and `resizable` and `detached` from `ArrayBuffer.prototype`. The `resizable` getter throws on a `SharedArrayBuffer`, so it is also the shared-buffer check. The package never reads `value.length`, because an own property or a subclass getter can report a length that `set` doesn't copy. It never uses `instanceof`, which rejects a `Uint8Array` from another realm and accepts a Proxy. It calls no method on a caller's array, because `subarray` runs a subclass's species getter. It copies a caller's bytes only with `set` on its own memory view. The options object must have `Object.prototype` or `null` as its prototype, so options that inherit a `context` fail instead of signing under the empty context. A call runs the read step (shape check, plain-object check, `Reflect.ownKeys`, unknown-key check, and one own-property read per known key), the input checks, the zero checks, and then the core, which reads only the fixed-length views that the checks built. No caller code runs after the read step. Because the API is synchronous, the core runs with no `await` between message chunks, so no other code runs while the instance is mid-operation. A runtime without one of the six getters fails the import, the same way a blocked compile does. The import is the load, so a static importer can't catch that failure, and `import()` rejects with it.
- **Errors.** In `sign`, the read step throws `TypeError` for the options shape, the prototype, or an unknown key. In `keygen` and `sign`, the input checks throw `TypeError` for a missing input, a wrong type, or a bad backing, and `RangeError` for a wrong length, and the zero checks throw `RangeError`. The checks run in a documented order, and their messages hold only package constants, computed numbers, and `typeof` results. Every other failure is a plain `Error` with the original in `cause`. Exceptions from the caller's own getters or proxy traps while the options are read propagate unchanged, as they do from platform APIs that read an options dictionary. So does the engine's own `TypeError` for an invalid trap result, such as an `ownKeys` trap that returns `[1]`. So `sign` can throw those besides `TypeError`, `RangeError`, the plain `Error`, and the engine's own stack-overflow error. `keygen` runs no caller code. `verify` returns `false` instead of throwing.
- **Randomness.** `randomness` is required: 32 bytes, or `"deterministic"`. An all-zero seed or randomness throws `RangeError`. Record 0004 holds the reasons for taking both values from the caller.
- **Packaging.** The package is an ES module only, and CommonJS is unsupported. The `exports` map nests `types` inside a `workerd` block and an `import` block, with no `default` or top-level fallback. The `workerd` entry imports the `.wasm` file and the default entry embeds it, and the check proves that the two are byte-identical.
- **Threat model.** The package guards against caller mistakes, such as wrong types, wrong lengths, and unknown options, and against secrets left in wasm memory after a call. It trusts the other JavaScript in the same realm and calls built-ins directly. So code that modifies a built-in, such as `Uint8Array.prototype.fill`, can change what the package does, the wipe included. Options are read only as own properties of a plain object, so a value added to `Object.prototype` can't supply an option. The exported objects, their `lengths`, and their functions are frozen, because every importer shares them. A mistaken write then throws a `TypeError` in strict-mode code, which includes every ES module. In sloppy-mode code, the write fails silently, and the object still doesn't change. A consumer who stubs `sign` in a test mocks the module, because a spy can't redefine a property of a frozen object. The README shows this factory form, which keeps the real implementation, records calls, and allows a stub:

  ```ts
  vi.mock("ml-dsa", async (importOriginal) => {
  	const real = await importOriginal<typeof import("ml-dsa")>();
  	return { ...real, mlDsa87: { ...real.mlDsa87, sign: vi.fn(real.mlDsa87.sign) } };
  });
  ```

  Plain `vi.mock("ml-dsa")` also works, but it replaces every function with a stub that returns `undefined`. The README doesn't suggest `vi.mock("ml-dsa", { spy: true })`, because in Vitest 5.0.3 it silently leaves the functions inside a frozen object unspied, and the test fails only later, with "is not a spy".

- **Verification.** ACVP's four files and Wycheproof run through the narrowest path that produces each expected output, by a total, exclusive routing table, with coverage credited per segment of the public path. noble 0.7.1 is the differential reference on a seeded, fixed case list in every runtime.

## Considered options

- **Branded types with `from` constructors and positional arguments.** Brands catch a swapped seed and randomness, and a key of the wrong parameter set, at compile time. But they exist only at compile time, add a `from` call to every call site, and can't apply to `verify`, which takes plain bytes from the network.
- **A fixed message cap in a fixed memory.** Over the cap, `verify` would either return `false` for a valid signature or throw, but `verify` must answer `false` instead of throwing for any input.
- **Growable memory.** It removes the cap with upstream's own framing, but memory grows with each message, and it reopens the fixed-memory decision and its checks.
- **A public `signMu` and `verifyMu`.** The package couldn't check that a caller's mu equals the hash of the public-key hash, the prefix, and the message, so every framing guarantee that ACVP proves for the public path would become the caller's job. Reopen when a consumer must compute mu apart from the signing key, the split that FIPS 204's external-mu variant exists for, with its own record that covers the binding checks.
- **A streaming signer.** It needs a state design that no consumer has asked for: where the public SHAKE256 state lives between calls, whether upstream's context is plain data that can be copied out of wasm memory and back in, how the final call binds the seed to the public key that started the stream, and what happens to an open signer when the instance is replaced. Such a signer can hold no secret between calls. Reopen when a consumer must sign data it can't hold in memory at once, with its own record.
- **Importing or exporting an expanded secret key.** It needs validation of imported keys with `pk_from_sk` and a key-validation export. Reopen when a consumer must interoperate with keys stored in the expanded FIPS 204 format, with a record that covers both.
- **HashML-DSA.** The composite signs pure ML-DSA, and HashML-DSA would add an API for the hash choice, four exports per parameter set, and 315 more ACVP cases to run.
- **Compiling on the first call.** A blocked compile would then make every `verify` return `false` without an error.
- **A CommonJS build.** It breaks the rule that the package ships as a plain ES module, and it adds the dual-package hazard.
- **Accepting shared or resizable buffers.** Another thread could grow a shared input between the check and the copy, and a getter could shrink a resizable buffer so that an input reads as empty.
- **Three prefix exports.** The three copies have identical bodies, and the vectors for every parameter set already exercise the one that's exported.
- **An integrity property against modified built-ins.** A capture module would hold every built-in the package calls, called through a captured `Reflect.apply`, without the iteration protocol, species-dependent methods, inherited reads, or coercion of caller values. A counting patch test and lint bans on globals, members, and syntax would prove that later changes to built-ins don't change the package's checks, errors, or outputs. The threat model trusts the code that would make those changes. The design also needed a syntax lint that oxlint 1.88.0 lacks, a test that patches the test runner's own built-ins, and review rules for every expression that touches a caller value. The parts that guard caller values stay as input rules.
- **Wrapping exceptions from the caller's getters.** The read step would catch them and throw a plain `Error` with the original in `cause`, so `sign` would throw only what `keygen` throws. Platform APIs that read an options dictionary pass such exceptions through unchanged, and a caller who throws their own error type expects to catch that type.
- **Unfrozen exports.** Consumer tests could spy on `sign`, but one importer's mistaken write would change the objects for every other importer.
